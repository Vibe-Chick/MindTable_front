# --- 백엔드 (MindTable_back, Django + DRF + SimpleJWT, http://127.0.0.1:8000 — Vite 프록시로 /api 전달) ---
# 화면별 정리는 Notion "API 명세서"와 동일. 토큰 O = Authorization: Bearer <access> 필요 (src/service/api.js 인터셉터가 자동 첨부)
#
# [회원가입]
# POST  /api/auth/google/              토큰 X   { credential }  → { access, refresh, user{id,email,name,picture,google_id}, created }   [Done]
# POST  /api/auth/school/send-code/    토큰 O   { school_email }  → { message }                                                       [Done]
# POST  /api/auth/token/refresh/       토큰 X   { refresh }  → { access }   access 만료(401) 시 프론트가 자동 호출 후 원래 요청 재시도 (SimpleJWT TokenRefreshView)   [백엔드 미구현]
# POST  /api/auth/school/verify-code/  토큰 O   { school_email, code, school_name, major }  → { school_verification: { school_email, school_name, verified_at } }   [Done]
#
# [심리 테스트]  (질문은 백엔드가 문항마다 LLM으로 생성, id 는 백엔드 내부 관리 → 프론트는 질문 문자열·답변만 주고받음)
# POST  /api/psychology/questions/     토큰 O   {}  → { questions: '질문 문자열' }   문항마다 호출(3회), 호출할 때마다 다른 질문
# POST  /api/psychology/check-answer/  토큰 O   { question, answer }  → { needFollowUp, followUpQuestion|null }   답변 검증 + 애매하면 꼬리 질문 생성 (테스트당 최대 1개 = 4번째 문항)
# POST  /api/psychology/analyze/       토큰 O   { user_id: <이메일> }  → { bigFive, interests, summary, valid, insufficient[] }   AI 성향 분석 (모든 답변은 check-answer 때 백엔드가 저장, 꼬리 답변은 questionId 'q1-f')
# POST  /api/users/{id}/profile/       토큰 O   profile  → { ok }                                                분석된 프로필 저장
#
# [매칭]  (테이블 방식: 한 명이 날짜·시간·인원을 정해 테이블을 열고, 다른 사람이 신청해 채운다. 정원이 차면 AI가 조합 이유·아이스브레이커 생성)
# POST  /api/match/request/            토큰 O   { userId, slots: ['2026-09-25-lunch'], sameSchoolOnly, capacity }  → { matchId, status: 'open' }
#                                                 테이블 만들기. slots 는 1개(7일 칩 또는 달력 28일), capacity 3~6 (나 포함), sameSchoolOnly 는 학교 인증 사용자만 true
# GET   /api/match/{id}/               토큰 O   → { status: 'open'|'done'|'cancelled', result: { id, hostId, mealAt, capacity, sameSchoolOnly, members[{ id, name, major, school, interest, isHost }], reason, scores, icebreakers } }
#                                                 테이블 상세/상태. open 동안 reason/scores 는 null, icebreakers 는 [] · mealAt 은 리뷰 창 계산용
# GET   /api/match/open/               토큰 O   → [{ id, mealAt, capacity, memberCount, sameSchoolOnly, host{ name, school, major }, joined }]
#                                                 열린 테이블 목록 (정원 미달만, mealAt 오름차순). sameSchoolOnly 테이블은 같은 학교 인증 사용자에게만 노출
# POST  /api/match/{id}/join/          토큰 O   {}  → { status: 'open'|'done', memberCount, capacity }
#                                                 테이블 신청. done 이면 곧바로 GET /match/{id}/ 로 결과 조회 · 400: 이미 신청/정원 마감/시간 겹침, 403: 같은 학교 전용
# GET   /api/match/{id}/recommend/     토큰 O   → [{ ...열린 테이블 항목, fit, fitReason, sharedInterests[] }]   ({id} = 내 user id)
#                                                 AI 추천 테이블. 저장된 내 프로필(interests·summary·bigFive)과 참가자 프로필을 비교해 fit(0~1) 내림차순. 프로필 없으면 400
#
# [식당 추천]  (흐름: 멤버 각자 조건 제출 → 전원 제출되면 AI가 식당 한 곳 추천 → 예약 → 확정. 투표 없음. {id} = 매칭(테이블) id, status 가 done 인 테이블만)
# POST  /api/match/{id}/restaurants/preferences/   토큰 O   { location: 'my-school'|'midpoint'|'custom', customLocation, price: 'low'|'mid'|'high', avoid }  → { submitted, total, common: { location, price, avoid } }
#                                                 그룹 조건 제출. customLocation 은 location='custom' 일 때만(지명 문자열), avoid 는 못 먹는 음식 자유 입력('' 가능)
#                                                 응답 submitted/total = 제출한 멤버 수/정원, common = 지금까지 제출된 조건의 교집합 (location 은 표시용 지명 문자열 예: '왕십리역 인근', price 는 겹치는 예산대, avoid 는 합집합)
# GET   /api/match/{id}/restaurants/               토큰 O   → { status: 'waiting'|'done', submitted, total, common, source: 'partner'|'map'|null, restaurant: { id, name, cuisine, walk, price, discount|null, hue: [색1, 색2], lat, lng }|null, reason }
#                                                 AI 추천 식당 (한 곳). 프론트가 대기 화면에서 2초마다 폴링 → 전원 제출 전엔 waiting(restaurant null), 전원 제출되면 AI가 common 조건으로 제휴 DB 에서 한 곳 선택 → 없으면 지도 API 로 근처 식당 한 곳 (source 'map', discount null)
#                                                 reason 은 AI 가 고른 이유 한 문장. 한 번 done 이면 같은 restaurant 를 계속 반환 (멤버마다 같은 결과) · walk '7분' 같은 도보 시간 문자열, hue 는 썸네일 그라데이션 hex 2개, lat/lng 지도 표시용
# POST  /api/match/{id}/reserve/                   토큰 O   { restaurantId }  → { ok, reservationId }
#                                                 추천 식당 예약. done 을 본 멤버마다 호출될 수 있으니 멱등 처리(이미 예약됐으면 같은 reservationId 반환) · 추천된 식당과 다른 id 면 400
#
# [마이페이지]
# PATCH /api/users/{id}/               토큰 O   { ...patch }  → user            내 정보 수정
# GET   /api/users/{id}/matches/       토큰 O   → [{ id, role: 'host'|'member', status, mealAt, capacity, memberCount, restaurant|null }]   매칭 기록 (mealAt 내림차순)
#
# [테이블 리뷰]
# GET   /api/match/{id}/review/        토큰 O   → { submitted, result }                                                    리뷰 제출 상태
# POST  /api/match/{id}/review/        토큰 O   { answers }  → { deltas, before, after, diversityPref, summary, driftAlert }   테이블 리뷰 제출 → 프로필 반영
# GET   /api/users/{id}/reviews/       토큰 O   → [{ matchId, date, restaurant, deltas, diversityPref, driftAlert }]        내 리뷰 기록
#
# [푸시 알림]  (백엔드: pywebpush + VAPID 키 필요)
# POST   /api/push/subscribe/          토큰 O   PushSubscription.toJSON() = { endpoint, keys: { p256dh, auth } }  → 사용자·기기별 저장
# DELETE /api/push/subscribe/          토큰 O   { endpoint }
# PATCH  /api/push/preferences/        토큰 O   { enabled, match_done, place_confirmed, review_request }
#   발송 시점: 매칭 완료 · 투표로 장소 확정 · 식사 2시간 후 리뷰 요청
#   payload: { title, body, url, tag? }  → public/sw.js 가 OS 알림으로 표시, 탭하면 url 로 이동
#
# ※ {id} 경로는 백엔드에서 토큰의 user와 {id} 일치 여부를 검사할 것
# ※ 모든 경로는 끝 슬래시(/)로 통일 (Django APPEND_SLASH — POST/PATCH는 슬래시 없으면 실패)
